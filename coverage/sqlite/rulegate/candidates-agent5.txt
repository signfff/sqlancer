# Candidate rules involving CAST (agent1, round 5). Nothing here has been run yet: every rule should go through rulegate.
# Facts and assumptions used throughout:
#   - In a comparison, if either side has INTEGER/REAL/NUMERIC affinity, NUMERIC affinity is applied to the other side.
#     Otherwise, if one side is TEXT and the other has none, TEXT affinity is applied. As I recall sqlite3CompareAffinity,
#     INTEGER, REAL and NUMERIC are interchangeable for this purpose.
#   - So (cast_int <0/1/NULL expr>) => <expr> is UNSOUND, even though the value is the same. (istrue x) = '1' compares int 1 with TEXT '1' and gives 0,
#     whereas CAST(x IS TRUE AS INTEGER) = '1' applies numeric affinity to '1' and gives 1. The same applies to casting bitand/concat results, and to moving a cast
#     out of or into coalesce/case without keeping an outer cast. None of those are proposed.
#   - Contexts that ignore affinity: NOT, IS TRUE/FALSE, ISNULL, CASE conditions, & | ~ (sqlite3VdbeIntValue), || (stringify), and the truth test (sqlite3VdbeRealValue).
#   - Collation of an integer/real value pair never matters.
#   - Compositions I checked and REJECT as unsound:
#       cast_int(cast_real x) vs cast_int x ('1e3' gives 1000 vs 1); cast_int(cast_text x) (REAL 1e20 gives 1 vs MAX); cast_real(cast_text x) (0.30000000000000004 becomes 0.3);
#       cast_numeric(cast_real x) (int64 MAX becomes REAL, not INTEGER); cast_int(cast_numeric x) ('1e3'); cast_int(neg x) vs neg(cast_int x) (saturation);
#       (+ (cast_numeric x) y) => (+ x y) ('1e3'+0 gives 1000.0, while CAST AS NUMERIC gives 1000); dropping cast_int inside rem or + (they use real/numeric conversion, not IntValue).

## Idempotence and collapsing compositions (same value, same affinity class, collation passes through CAST the same way)

cast-real-idem ; (cast_real (cast_real ?x)) => (cast_real ?x)
#   CAST of a REAL (or NULL) AS REAL is the identity. The affinity is REAL on both sides, and the implicit collation passes through either way.
cast-text-idem ; (cast_text (cast_text ?x)) => (cast_text ?x)
#   CAST of TEXT AS TEXT is the identity. The affinity is TEXT on both sides.
cast-blob-idem ; (cast_blob (cast_blob ?x)) => (cast_blob ?x)
#   CAST of a BLOB AS BLOB is the identity. The affinity is BLOB on both sides.
cast-numeric-idem ; (cast_numeric (cast_numeric ?x)) => (cast_numeric ?x)
#   The first cast yields an INTEGER, or a REAL that it already declined to convert to INTEGER. Casting INTEGER AS NUMERIC is the identity, and the same convertibility test should keep the REAL as REAL.
#   UNSURE: this relies on CAST-from-TEXT and CAST-from-REAL using the same "REAL is an exact integer" test (sqlite3RealSameAsInt, |r| < 2^51). Test it with 2^51..2^63 boundaries and '1e3'.
cast-numeric-of-int ; (cast_numeric (cast_int ?x)) => (cast_int ?x)
#   CAST of an INTEGER AS NUMERIC is the identity. NUMERIC vs INTEGER affinity is the same class in comparisons.
#   SLIGHTLY UNSURE: this depends on that affinity-class claim. It fails if any comparison path distinguishes INTEGER from NUMERIC affinity.
cast-real-of-numeric ; (cast_real (cast_numeric ?x)) => (cast_real ?x)
#   CAST AS NUMERIC yields either the integer that the text denotes exactly or the same double that sqlite3AtoF gives, so converting to REAL gives the same double as parsing the text directly ('12abc' gives 12.0, '1e3' gives 1000.0, int64 MAX gives 9.223372036854775807e18).
#   UNSURE: digit strings longer than 19 digits, and whether int64 -> double rounding matches sqlite3AtoF's rounding for 16-19 digit strings.
cast-blob-of-text ; (cast_blob (cast_text ?x)) => (cast_blob ?x)
#   CAST AS BLOB of a non-BLOB value first applies TEXT affinity (the same stringify as CAST AS TEXT) and then relabels the bytes. The affinity is BLOB on both sides.
cast-text-of-blob ; (cast_text (cast_blob ?x)) => (cast_text ?x)
#   cast_blob keeps the bytes of the value's text form in the database encoding, and cast_text reads those bytes back in the same encoding. So the result is the same text as casting x directly. The affinity is TEXT on both sides.

## NULL in, NULL out (results are 0/1, so affinity does not matter)

isnull-cast-int ; (isnull (cast_int ?x)) => (isnull ?x)
#   CAST never turns a non-NULL value into NULL ('abc' gives 0, and a REAL saturates), and NULL stays NULL.
isnull-cast-real ; (isnull (cast_real ?x)) => (isnull ?x)
#   'abc' gives 0.0, and huge text gives Inf, not NULL. NaN cannot arise from parsing.
isnull-cast-text ; (isnull (cast_text ?x)) => (isnull ?x)
#   Every non-NULL value has a text rendering.
isnull-cast-numeric ; (isnull (cast_numeric ?x)) => (isnull ?x)
#   Same argument as cast_int/cast_real.
isnull-cast-blob ; (isnull (cast_blob ?x)) => (isnull ?x)
#   Every non-NULL value has a byte representation. An empty string gives an empty BLOB, which is not NULL.
isnotnull-cast-int ; (isnotnull (cast_int ?x)) => (isnotnull ?x)
#   This is the complement of isnull-cast-int. The same rule works for the other four targets. It may be derivable through not-isnull; drop it if so.

## Dropping a cast where the consumer applies the same conversion itself (the result is an integer, text or truth value, so affinity is irrelevant)

bitand-drop-cast-int ; (bitand (cast_int ?x) ?y) => (bitand ?x ?y)
#   & converts each operand with sqlite3VdbeIntValue, which is the same conversion CAST AS INTEGER uses (text takes the leading integer prefix, a REAL truncates or saturates, a BLOB is read as text). The result is an integer.
#   SLIGHTLY UNSURE: this assumes OP_Cast to INTEGER and OP_BitAnd share sqlite3VdbeIntValue/memIntValue. Test it with '1e3', ' 12', '0x10', 1e20 and x'3132'. The same rule works for the right operand.
bitor-drop-cast-int ; (bitor (cast_int ?x) ?y) => (bitor ?x ?y)
#   Same argument and same uncertainty as bitand-drop-cast-int.
bitnot-drop-cast-int ; (bitnot (cast_int ?x)) => (bitnot ?x)
#   ~ uses sqlite3VdbeIntValue. Same argument and same uncertainty.
concat-drop-cast-text-left ; (concat (cast_text ?x) ?y) => (concat ?x ?y)
#   || stringifies numbers with the same routine as CAST AS TEXT, and reads BLOB bytes as text in both cases. The || result has no affinity and no implicit collation, so the implicit collation that the cast would carry is lost either way.
concat-drop-cast-text-right ; (concat ?x (cast_text ?y)) => (concat ?x ?y)
#   Same argument for the right operand.
istrue-drop-cast-real ; (istrue (cast_real ?x)) => (istrue ?x)
#   The truth test (sqlite3VdbeBooleanValue) checks an INTEGER for != 0 and otherwise uses sqlite3VdbeRealValue != 0. CAST AS REAL uses the same RealValue, and an int64 is non-zero iff its double is. The same rule works for isfalse/isnottrue/isnotfalse.
not-drop-cast-real ; (not (cast_real ?x)) => (not ?x)
#   NOT uses the same truth test, and the result is 0/1/NULL.
case-cond-drop-cast-real ; (case (cast_real ?c) ?a ?b) => (case ?c ?a ?b)
#   The CASE condition uses the same truth test. The branches are unchanged, and an explicit COLLATE inside c is seen through CAST the same way, so the collation search order is the same.
istrue-drop-cast-numeric ; (istrue (cast_numeric ?x)) => (istrue ?x)
#   CAST AS NUMERIC gives either the exact integer of the text, which is non-zero iff the double is, or the same double that RealValue gives.
#   UNSURE: the same AtoF-vs-integer concern as cast-real-of-numeric, for strings where those two might disagree on zero-ness. I believe they never do.

## Operand swaps that are safe without the collation guard, because both sides are numbers after the cast

eq-sym-cast-int ; (= (cast_int ?x) (cast_int ?y)) => (= (cast_int ?y) (cast_int ?x))
#   Both sides are INTEGER (or NULL) with the same affinity, and collation is never consulted for integer-vs-integer, even if the cast carries a column's implicit collation. The same rule works for <> and is/isnot.
lt-sym-cast-int ; (< (cast_int ?x) (cast_int ?y)) => (> (cast_int ?y) (cast_int ?x))
#   Same argument for ordering. The same rule works for <= >= >.
eq-sym-cast-real ; (= (cast_real ?x) (cast_real ?y)) => (= (cast_real ?y) (cast_real ?x))
#   REAL vs REAL, with no collation involved. The same rule works for the order comparisons, and for cast_numeric (INTEGER/REAL values only).

## Pushing a cast into branches while KEEPING the outer cast (so affinity and implicit collation of the whole expression are unchanged)

cast-int-into-coalesce ; (cast_int (coalesce ?a ?b)) => (cast_int (coalesce (cast_int ?a) (cast_int ?b)))
#   cast_int is idempotent (already passed) and NULL-preserving, so coalesce falls through on the same rows. The outer CAST keeps INTEGER affinity. coalesce blocks implicit collation in both forms, and the explicit-COLLATE order is a,b on both sides.
cast-int-into-case ; (cast_int (case ?c ?a ?b)) => (cast_int (case ?c (cast_int ?a) (cast_int ?b)))
#   Same argument. The branch selection is unchanged.
cast-text-into-coalesce ; (cast_text (coalesce ?a ?b)) => (cast_text (coalesce (cast_text ?a) (cast_text ?b)))
#   Same argument, using cast-text-idem. The same rule works for cast_real/cast_blob and the case variants. It does NOT work for cast_numeric unless cast-numeric-idem passes.
