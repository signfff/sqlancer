## 二、候选方向

### A. 让工作负载跟上语言（最便宜，立刻见效）
- **问题**：语言已扩到 IS/CASE/IN/LIKE/函数/CAST/COLLATE，但 72% 的流量来自偏覆盖率的语料，随机生成那 28% 又被谓词过滤器筛过（会拒收位运算、unary 负号等，即审查时的 C1 项），所以新节点几乎没被喂到。
- **做法**：
  1. 调整来源配比，提高随机生成的比例；
  2. 放开谓词过滤器对位运算和负号的限制，因为这些现在都有节点和规则了；
  3. 检查随机生成器为什么几乎不出现 IS/LIKE：生成器里有这些运算符，但真实流量里是 0，需要定位是过滤器还是可满足性筛查拦掉的；
  4. 给语料加一个"按结构补充"的入口。
- **工作量**：小（1–2 天）。
- **收益**：让那 111 条闲置规则用起来，并让 IS/LIKE/IN 这些历史上 bug 多的区域真正被测到。能否多抓到 bug 无法保证，但这是其他方向的前提，否则新加的规则仍然用不上。

### B. 把规则验证升格为"规格差分测试"（已被 002 证明有效）
- **问题**：002 说明，"按文档成立的等式在 SQLite 上不成立"本身就是 bug 信号。目前这只是规则扩张的副产品。
- **做法**：让 agent 系统地读 SQLite 文档（datatype3 的亲和性和排序规则、lang_expr 的各运算符、各内置函数、IN/BETWEEN/CASE 的定义），把文档里的每条语义断言写成等式，交给 rulegate 在 trunk 上逐一验证。失败的条目按"违反文档"还是"违反规则作者的假设"分流，前者人工确认后报告。历史上第一关失败的约 17 条也按这个标准复核一遍。
- **工作量**：小到中。rulegate 现成可用，主要是 agent 的提示词和分流流程。
- **收益**：从单位投入看，这个方向出 bug 的效率可能最高。它直接比较规格和实现，覆盖面也不局限于 WHERE 改写（函数语义、类型转换都能测）。对论文而言，"由 LLM 从文档导出蜕变关系、再在真实引擎上差分验证"是一个清楚的方法贡献，而且已经有一个真实 bug 作为证据。

### C. 行值与子查询进入 e-graph
- **问题**：行值查询占 3.1%，目前**完全拿不到变体**；IN (SELECT) 6.2%、EXISTS 2.0%，现在都是不透明原子，只能靠 e-graph 之外的拆解处理。这两块都是 SQLite 历史上 bug 最多的区域。
- **做法**：
  1. 行值等值展开 `(a,b)=(c,d)` ↔ `a=c AND b=d`。三值逻辑下是对的（行值等于为 NULL 的条件和 AND 一致），但行值的 `<` 展开在 NULL 下不对，只能用基于 IS 的写法；
  2. 在真值上下文里做 EXISTS ↔ IN (SELECT) 互换。两者的亲和性和排序规则规则不同，需要闸门；
  3. 需要"关系原子"节点，带相关变量。
- **工作量**：中。规则不多（agent 估计 15–30 条），但每条都要谨慎加闸门，rulegate 也要能生成子查询上下文。
- **收益**：直接打到 bug 高发区，而且让 3.1% 现在完全测不到的查询有了变体。

### D. 表结构感知，配合 e-class 分析
- **问题**：最能改变执行计划的改写，现在都因为"不知道列的排序规则、亲和性、NOT NULL、有哪些索引"而被禁用。例如 OR ↔ IN、排序规则一致时自由交换、用 `x+0` 或 `x||''` 让列用不上索引、对 NOT NULL 列去掉 IS NOT NULL、匹配部分索引的条件。
- **做法**：Java 端每次请求附带列的元数据；服务端加一个 e-class 分析，记录"取值是否只有 0/1/NULL""能否为 NULL""亲和性和排序规则从哪来"，规则变成带条件的；rulegate 也要支持带表结构的判定。
- **工作量**：中到大，Java、Rust 和检查工具都要改。
- **收益**：最贴近当前真实 bug 的分布，比如论坛上那个还开着的"LEFT JOIN + IN + 双列索引"bug，正是执行计划和索引选择出的问题。e-class 分析本身还能把约 60 条按节点重复写的规则合并成约 10 条通用规则。

### E. 跳出 WHERE 改写（战略层面）
- 外部最近的 bug 多在 DDL/DML 状态、存储、JOIN 上，单表 WHERE 等价改写从结构上就碰不到。
- 要覆盖这些，需要别的判定器（例如 DDL 前后状态一致、事务和保存点回放、JOIN 重排），这已经超出"规则"这条线。这里只记下来，作为论文讨论"方法边界"时的素材。

## 三、建议的顺序

1. **A 先做**（1–2 天）：否则新语言和新规则白做，后面方向的效果也无从测量。
2. **B 紧接着做**：成本低，已经证明能出 bug，论文价值明确。
3. **C 再做**：补上 3.1% 完全没有变体的行值查询，打 bug 高发区。
4. **D 作为中期工程**：e-class 分析可以先做一个最小版本（0/1/NULL 和可空性），为表结构感知铺路。
5. **E** 作为长期讨论。
